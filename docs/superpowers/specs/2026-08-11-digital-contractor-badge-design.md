# 數位承攬商識別證（QR 發證）— 設計文件

日期：2026-08-11
狀態：設計確認中

## 背景與動機

訓練表單已改成測驗滿分才能送出，送出即代表這個人完成當次教育訓練。現在要讓他在入廠時能出示證明：送出成功後產生 QR，本人掃描後開啟一張「數位承攬商識別證」，門口警衛看證上的姓名、廠商與有效期限即可放行。

整個產品要放上 GitHub Pages，沒有後端也沒有資料庫，所以識別證的內容只能由 QR 掃出來的網址自己帶。這個前提決定了下面所有設計，也決定了它擋不住什麼（見「已知限制」）。

## 需求決策

| 項目 | 決定 |
|---|---|
| 有效期 | 訓練完成日起算 3 年（對應法規的三年內 6 小時安全衛生教育訓練） |
| 身分證顯示 | 部分遮蔽 `A12****789`，全碼不進 QR |
| 照片欄 | 用現有的 Realtek logo 當佔位圖，不處理真人照片 |
| 證上小 QR | 指向同一張識別證的網址，警衛可自行掃描 |
| 檔案結構 | 新增 `badge.html` 與 `badge.js`，交付從 1 個檔變 3 個 |
| 防篡改 | 加校驗碼，改網址任一欄就顯示驗證失敗 |
| 證上欄位 | 姓名、身分證、廠商名稱、有效期限、發證時間、持證須知 |
| 成功畫面 | 識別證預覽、大 QR，加上開啟／下載 PNG／列印三顆按鈕 |
| 版面實作 | inline SVG，畫面、PNG、列印共用同一份 |

持證須知固定文字：須遵守瑞昱所制定之施工規範進行施工。

## 設計

### 一、檔案結構

```
index.html   訓練表單（現有，成功畫面加識別證區塊）
badge.html   識別證頁，掃 QR 後開啟的目標
badge.js     識別證版面、QR 產生、校驗碼，兩頁共用
```

`badge.js` 共用是為了讓成功畫面能直接顯示同一張識別證並下載 PNG；不共用就得把版面寫兩份，之後改版必然漏掉一邊。

Realtek logo 的 base64 會在 `badge.js` 內另存一份常數給識別證用，`index.html` 導覽列維持現有的內嵌寫法不動。代價是 logo 在交付內容裡出現兩次，多約 38 KB；換得的是不必動已驗證過的表單程式碼。

### 二、識別證網址與 payload

```
https://<站台>/badge.html#d=<base64url(JSON)>.<8 碼校驗碼>
```

資料放在 `#` 之後，瀏覽器不會把 fragment 送給伺服器，GitHub Pages 的存取記錄裡不會出現姓名與廠商。

JSON 欄位（縮寫是為了讓 QR 的模組數少一點、好掃）：

| key | 內容 | 範例 |
|---|---|---|
| `v` | 格式版本 | `1` |
| `n` | 姓名 | `王小明` |
| `i` | 遮蔽後身分證 | `A12****789` |
| `c` | 廠商名稱 | `○○工程有限公司` |
| `t` | 訓練完成日 | `2026-08-11` |
| `e` | 有效期限 | `2029-08-11` |
| `s` | 發證時間（UTC+8） | `2026-08-11T14:32` |

發證時間固定以台北時間（UTC+8）產生，不跟著裝置時區跑：把當下的 UTC 毫秒加上 8 小時再格式化。裝置設在別的時區的人，證上看到的仍是台灣時間。

同理，判斷有沒有過期時的「今天」也用 UTC+8 換算，避免同一張證在不同時區顯示不同狀態。

遮蔽規則：10 碼身分證取前 3 碼 ＋ 4 個 `*` ＋ 後 3 碼。全碼只在表單送出時進 Google 試算表，不進 QR。

站台網址用 `new URL('badge.html', location.href)` 動態組出來，本機 http.server、GitHub Pages、內部伺服器都不用改設定。

### 三、校驗碼

`sig = fnv1a32(BADGE_KEY + payloadB64)`，輸出 8 碼 hex，附在 payload 後面。開啟識別證頁時重算比對，不符就顯示「識別證驗證失敗，請重新完成訓練」的錯誤卡片，不渲染任何欄位。

密鑰寫在 `badge.js` 裡，和測驗答案的混淆同一個等級：擋得住隨手改網址的人，擋不住願意讀原始碼的人。

### 四、有效期與狀態顯示

到期日 = 訓練完成日 `setFullYear(+3)`。2 月 29 日受訓會落在 3 月 1 日，這是 JS 的自然行為，接受。

狀態判斷比較 UTC+8 的當下日期與 `e`，到期日當天仍算有效。

顯示規則分兩種，因為狀態只會單向腐化——「有效」會過期，「已過期」不會變回有效：

- **網頁版**：即時計算，綠色「有效」或紅色「已過期」＋卡片轉灰。掃 QR 看到的永遠是準的。
- **PNG 與列印版**：不畫綠色「有效」，改成中性的「有效期限 2029-08-11」＋小字「即時狀態請掃描 QR 驗證」。只有在產生當下就已過期時才蓋紅色「已過期」，這個印記不會腐化。

PNG 檔名帶到期日：`承攬商識別證_王小明_有效至2029-08-11.png`。

這條規則是為了避免一張躺在相簿裡兩年的圖片上有一顆騙人的綠燈。

### 五、識別證版面

直式卡片，viewBox `340 × 540`，深藍漸層底，依 mockup：

```
┌─────────────────────────┐
│   瑞昱數位承攬商識別證   │  標題列
├─────────────────────────┤
│ ┌──────┐    ┌────────┐  │
│ │ logo │    │ 小 QR  │  │  左：Realtek logo 當照片欄
│ └──────┘    └────────┘  │  右：小 QR ＋「掃碼驗證 | SCAN」
│              狀態徽章    │
├─────────────────────────┤
│ 姓名 NAME:              │
│ 身分證 ID NO:           │
│ 廠商名稱 COMPANY:       │
│ 有效期限 VALID UNTIL:   │
│ 發證時間 ISSUED:        │
├─────────────────────────┤
│ 持證須知：須遵守瑞昱…    │
└─────────────────────────┘
```

同一份 SVG 三用：

- 畫面：直接插進 DOM
- PNG：序列化成 data URI 餵給 `Image`，畫進 2 倍解析度的 canvas（680 × 1080），`toBlob` 後下載
- 列印：`@media print` 只留卡片，其餘全部隱藏

SVG 轉圖時瀏覽器不會載入外部字型，所以識別證的 `font-family` 直接寫系統中文字型串列（`Microsoft JhengHei`、`PingFang TC`、`Noto Sans TC`、`sans-serif`），不依賴 Google Fonts。畫面與 PNG 的字型因此一致。

### 六、QR 產生器

內嵌一份 MIT 授權的 QR 產生器（`qrcode-generator` 等級，約 4 KB），只用它算出模組矩陣，再由 `badge.js` 畫成 SVG 的 `rect`。授權聲明保留在檔頭。

不使用任何線上 QR 服務——那等於把姓名與廠商送給第三方，也讓內部無外網的環境無法使用。

錯誤修正等級 M，payload 約 150–200 字元，實測需確認在手機上好掃。

### 七、成功畫面

測驗滿分並送出後，現有的成功卡片下方加一區：

- 識別證預覽（同一份 SVG，縮小顯示）
- 大 QR，附說明「請用手機掃描，開啟你的數位識別證」
- 三顆按鈕：開啟識別證（新分頁）、下載識別證圖片、列印

同一台裝置填完的人沒辦法自己掃自己，所以「開啟識別證」按鈕是必要的，不是備援。

## 驗證方式

沿用現有的 Playwright 腳本（headless chromium），攔截 `docs.google.com` 避免測試資料進正式試算表：

1. 走完三步驟、測驗全對送出，確認成功畫面出現 QR、預覽與三顆按鈕
2. 從 QR 的資料重組網址開啟 `badge.html`，確認姓名、遮蔽身分證、廠商、到期日與發證時間都正確
3. 竄改 payload 任一字元，確認顯示驗證失敗且不渲染欄位
4. 用 `t` 設為 4 年前的資料開啟，確認顯示紅色「已過期」
5. 用 2024-02-29 當訓練日，確認到期日是 2027-03-01
6. 下載 PNG，確認尺寸 680 × 1080、中文沒有變成方框、未過期的圖上沒有綠色「有效」
7. 列印預覽只有卡片

## 已知限制

1. **可以自己造假證**。網址結構與密鑰都在前端，讀得懂原始碼的人能編出任意內容的合法網址。校驗碼只擋隨手竄改。
2. **過期可以規避**。狀態用裝置當下時間判斷，把手機時間往回調就會顯示有效。
3. **網址即個資**。QR 內容含姓名、廠商與遮蔽後身分證，網址被轉傳或截圖外流，這些資料一起走。
4. **PNG 是快照**。下載後的圖片不會自動更新狀態，這也是 PNG 版不畫綠燈的原因。
5. **證明的是訓練，不是資格**。保險證明、特殊作業證照這些仍靠現場抽查，識別證不代表已查核。

要真正防偽，需要後端發證與一支驗證 API（警衛掃描後由伺服器回答這張證是否存在、是否有效）。那超出 GitHub Pages 的能力範圍，列為後續。

## 範圍外

- 後端發證與驗證 API
- 真人照片
- 識別證撤銷或作廢
- 把同意個資宣告的紀錄寫進 Google 表單（已在 2026-08-11 決定不做）
- 警衛端的查驗介面

## 部署

GitHub Pages 從 repo 根目錄提供 `index.html`、`badge.html`、`badge.js` 三個檔。Settings → Pages 選定分支與 root 目錄即可，沒有 build step。目前工作分支是 `master`，上架前要確認 Pages 指到實際有檔案的那個分支。

交給內部 IT 的版本一樣是這三個檔，不需要任何設定。
